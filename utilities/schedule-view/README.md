# Schedule viewer

A single-file, offline viewer for SeQuant schedule documents (JSON,
`sequant.schedule/1`). It has no external resources and works from `file://`.

## Producing a document

A document is assembled from three APIs: `opt::schedule::record_root` and
`fingerprint_of` (`SeQuant/core/optimize/schedule_pin.hpp`) fill `roots` and
`fingerprint`, `eval::schedule::record_dag`
(`SeQuant/core/eval/schedule_dag_record.hpp`) fills `dag`, and `to_json`/`write`
(`SeQuant/core/eval/schedule_document.hpp`) serialize it. `example.json` is a complete two-root example (R1 and R2
share `X = g*t`, each batched on a different occupied index, with a `run`
section: `n_batches`, `footprint` and `builds` come from the ordered dry run,
`extents`, `batch_targets` and `planner` are hand-filled). It is regenerated by the hidden unit test

    SEQUANT_SCHEDULE_EXAMPLE_OUT=$PWD/utilities/schedule-view/example.json \
      build/tests/unit/unit_tests-sequant "[.write-example]"

## Opening the page

1. Embedded (preferred): `sequant-schedule view <doc.json> [--run run.json]
   [-o out.html]` writes a copy of `schedule-view.html` with the document (and
   the optional run section) inlined; open `out.html` in a browser. The page
   is compiled into the tool; `--template <file>` substitutes another copy.
2. File picker: open `schedule-view.html` directly and use "open file(s)" to
   load a document, optionally together with a run-section file (select both
   at once). The same control loads another document into an embedded page.

`sequant-schedule validate <doc.json>` checks a document and prints a summary.

A realistic document comes from the hidden `[dryrun-2iter-report]` unit test,
which runs the DF-CCSD doubles residual through the ordered executor as a dry
run at water-20 or C60 PNO-CCSD scale:

    SEQUANT_UT_DRYRUN_SYSTEM=c60 SEQUANT_UT_DRYRUN_BATCH=aux_pao_occ \
      SEQUANT_UT_SCHEDULE_DOC=$PWD/c60.json \
      build/tests/unit/unit_tests-sequant "[dryrun-2iter-report]"

(`SEQUANT_UT_DRYRUN_SYSTEM` is `water20` or `c60`, `SEQUANT_UT_DRYRUN_BATCH`
one of `none`, `aux`, `aux_occ`, `pao`, `aux_pao`, `aux_pao_occ`; the test
lists further knobs.)

## Using it

- Left: folding outline of blocks and the values built in them, in `steps`
  order; `read X[i]` rows are slice reads of a value homed in an outer block.
  Blocks open to nesting depth 1 (root and its direct children); click the caret to fold. The filter matches value id,
  expression, term key and root label (ancestors of matches stay).
- Right: neighbourhood of the selection (producers, selected, consumers) to the
  chosen depth (1 to 4). One box per node, one port `[i]` per value; boxes are
  tinted by home block; dashed connectors are sliced reads; `+n more` expands a
  truncated column.
- Clicking a row, a port, a box header or a block highlights the related rows
  and boxes everywhere; the inspector shows every field of the selection
  (siblings are links) and, when a run is loaded, `n_batches`, `footprint` and
  `builds`.
- Keyboard: `/` focuses the filter, `Esc` leaves it.
